# Constitution Generation (Greenfield)

## Purpose

The constitution captures the project's identity, principles, and constraints.
It's the foundation that propose uses to validate specs and check uses to validate code.

## Conversation Guide

Ask these questions (adapt to context, don't interrogate):

### Identity
1. **What are you building?** (one sentence)
2. **Who uses it?** (target audience)
3. **What problem does it solve?** (the "why")

### Principles (ask for 3-5)
Guide with examples:
- "Offline-first: must work without internet"
- "Privacy by default: no data leaves the device"
- "Convention over configuration: sensible defaults"
- "Speed over features: fast MVP, iterate later"

### Constraints
- **Technical:** language, framework, cloud provider, existing infrastructure
- **Organizational:** team size, timeline, compliance requirements
- **Non-functional:** performance targets, security requirements, accessibility

### Anti-goals (what this project is NOT)
- "Not a platform — single-tenant only"
- "Not real-time — batch processing is fine"
- "Not mobile — web only for v1"

## Output Format

Generate `specforge/constitution.md` with this structure:

```markdown
# [Project Name] — Constitution

## Identity
**What:** [one sentence]
**Who:** [target audience]
**Why:** [problem being solved]

## Principles
1. **[Principle name]** — [explanation]
2. **[Principle name]** — [explanation]
3. ...

## Constraints
- **Technical:** [list]
- **Organizational:** [list]
- **Non-functional:** [list]

## Anti-goals
- [what this project deliberately does NOT do]

---
*Generated by SpecForge on [date]. Human-approved.*
```

## Validation

Before presenting to the user, verify:
- At least 3 principles defined
- At least 1 technical constraint
- At least 1 anti-goal
- No contradictions between principles and constraints
