# SpecForge — Mental Model

> SpecForge makes specs executable enough to govern code.
> You approve artifacts. The CLI validates structure. Hooks prevent workflow drift.
> Code can change; the trace tells you whether the spec is still true.

If you read one page about SpecForge, read this one.

## The thesis

**The specification is the product. Code is a regenerable byproduct.**

Most workflows treat the spec as documentation that rots the moment code is
written. SpecForge inverts that: the spec is the source of truth, and the trace
keeps it honest as the code evolves.

## Four actors, four jobs

SpecForge works because it never asks one actor to do another's job.

| Actor | Job | Can it guarantee quality? |
|-------|-----|---------------------------|
| **You (human)** | Approve artifacts at gates | You decide what "good" means |
| **The LLM** | Produce and judge artifacts | No — it can be wrong; that's why gates exist |
| **`sf` (CLI)** | Validate structure, persist state, compute, render | Yes, for *structure* — deterministically |
| **Hooks** | Stop workflow drift (e.g. writing code before a gate) | Yes, for *sequence* — mechanically |

The honest line SpecForge draws: **structure is enforceable; quality is only
auditable.** The CLI can guarantee that a tasks file is well-formed and that every
requirement is covered by a task. It cannot guarantee the requirements are *good*
— that's what your gate approvals are for.

## The pipeline

```
sf-init  →  sf-propose  →  sf-build  →  sf-check
            requirements    waves        traceability
            design          (computed)   + verdict
            tasks
```

Each phase ends at a 🔴 **gate**: a human decision recorded in the ledger
(`features.json`). A gate is not a header in a markdown file claiming approval —
it's an auditable entry that says *who* approved *what*, *when*.

## The traceability spine

This is what keeps the spec true over time:

```
PR#  →  feature  →  R#  →  task  →  code  →  test
```

Every piece of shipped code links back to a requirement, and every requirement
links forward to the code and tests that satisfy it. When code drifts away from
the spec, `sf doctor --drift` and `sf trace verify` tell you — so you find out
the spec is stale *before* you trust it.

The spine is built **as you build**, not reconstructed afterward. During
`sf-build` each wave declares the exact test that proves every requirement it
touches, and `sf trace verify --contract` blocks the wave gate until that test
actually exists. "Test passing" is never assumed and never deferred to review:
**naming no test ≠ done**. `sf-check` later audits and seals what the build
declared — it doesn't invent the spine from scratch.

## JSON-first, Markdown-rendered

Artifacts have a JSON source of truth that the CLI validates, and a Markdown
render that humans read:

```
JSON source  →  sf validate  →  Markdown render
```

You never hand-edit the render and hope it matches. The JSON is canonical; the
Markdown is generated. This kills the drift between "what's visible" and "what's
real."

## Why this survives a lost conversation

A core design goal: **the conversation can disappear and SpecForge still knows
what to do.**

- Every phase is reconstructable from files on disk.
- Every gate lives in the ledger, not in chat history.
- The next valid action is *derived from state* (`sf state current`), not
  remembered from 30 turns ago.
- Sub-agents receive context generated by the CLI (`sf context for-wave`), not a
  human's summary.

That's the difference between a workflow guided by instructions and a system that
governs itself from durable state.

## What SpecForge is *not*

- Not an ecosystem configurator or a universal multi-agent installer.
- Not a fully automatic code generator that bypasses human judgment.
- Not a guarantee of code quality — it's a guarantee of *structure and sequence*,
  plus the trace to audit quality yourself.
